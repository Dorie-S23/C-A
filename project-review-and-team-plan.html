Specific code issues to include in implementation reviews

  • Keyboard choice selection: option buttons are created, but the dialogue’s global Enter/Space handler prevents default behavior and calls advance(), which deliberately does nothing on a choice. This can suppress native button activation. Add an explicit focus/selection model; test mouse, Tab, arrows, Enter, and Space in the real overlay.
  • Pause does not freeze gameplay: animate() calls updateMovers(delta) and the room update regardless of pointer lock. Hazards can move while a pause menu is displayed. Gate active gameplay updates/timers separately from harmless menu animation.
  • Large frame deltas: movement uses uncapped clock.getDelta(). Maze circle-vs-box resolution checks final position rather than sweeping the path; a large step can cross a wall or hazard. Clamp/substep movement and test after tab switching and stalls.
  • Input reset: movement flags are not cleared when the window loses focus, a dialogue opens, or Home is selected. Held input can survive missed key-up events. Centralize reset on those transitions.
  • Async room-load race: no request generation token/cancellation guards selectRoom(). An obsolete load completion could attach a room or show an overlay after another request or Home. Guard success and error handlers and dispose unused results.
  • Resource ownership: teardown traverses mesh resources but does not dispose shadow-map resources on lights or specialised reflection render targets. Maze materials are module-level shared objects that teardown also disposes; explicitly distinguish reusable resources from level-owned ones. Mirrors need their own disposal hook if integrated. Three.js resource disposal guide.
  • Per-frame allocation: collision queries allocate candidate arrays, raycast results, and fallback arrays; interaction focus calls flatMap() every frame. BVH acceleration is useful, but profile allocations and broadphase costs before further optimisation.
  • 3D movement depth: current player movement is mainly X/Z with floor following. Design a purposeful ramp/stair/elevated clue route in Level 2 to demonstrate vertical traversal, then test camera and collision there. Do not add flying or jumping unless it serves the game.
  • Interaction visibility: current focus tests only registered interactables and can ignore intervening world geometry. Add range and line-of-sight checks for clues/NPCs to avoid collecting through walls.
  • Credits completeness: the screen credits Three.js and Jacxx2’s walls but still has room/lobby TODOs and omits Caine and BVH attribution. The HTTP Creative Commons address is a hyperlink, not a loaded runtime asset; it is not evidence of a mixed-content asset failure.

These code observations identify implementation gaps or risks. Except for the reported Node checks/build failure, they have not been reproduced in a browser during this audit. The “60+ seconds” circus-loading note in main’s comment is historical; current load time must be measured rather than quoted as a fresh result.

10. A concrete scoring proposal to review

The storyline defines the two-meter logic but not its numeric thresholds, dialogue count, item bonuses, or search durations. The values below are a starting proposal, not existing behavior or a course requirement. Keep the meters hidden in the actual game; use this report’s simulator only for planning and QA.

Escape Threshold

Five graded Ribbit choices, +1 per good choice; three unique presented office pictures, +1 each. Maximum 8; proposed pass mark 6.

5 good + 1 picture passes; 3 good + 3 pictures passes; 5 good + 0 pictures fails; 0 good + 3 pictures fails. Every bad L1 choice still advances with zero points.

Jax’s Fate

Five graded final choices, +1 per good choice; +1 for each recovered memory item. Maximum 7; proposed save mark 4.

2 good choices + both items saves; 4 good choices + no items saves; items help but alone do not save him. Timeouts award zero and still progress.

Timer starting point: try 90 active-play seconds per item search, then tune using maze path length, camera_setup’s slower movement speed, and fresh-player playtests. At the proposed 2-unit/s walking speed, 90 seconds is about 180 units before detours. Do not keep main’s 6-unit/s walk and 15-unit/s sprint by accident if importing the camera branch; confirm movement and hazard balance together.
